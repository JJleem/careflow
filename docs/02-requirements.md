# 2. 전체 요구사항 목록

문제 정의(01-problem-definition.md)의 페인포인트(P1~P9)에서 도출한 전체 요구사항이다.
각 요구사항에 **근거가 되는 페인포인트**를 연결했고, MVP 포함 여부는 03-mvp-scope.md에서 우선순위 기준과 함께 판정한다.

- 우선순위: `Must`(MVP 필수) / `Should`(MVP 포함 권장) / `Could`(여력 시) / `Won't`(이번 범위 제외, 확장 설계만)

## 2.1 기능 요구사항 (FR)

### A. 계정 및 피검자 관리

| ID | 요구사항 | 근거 | 우선순위 |
|----|---------|------|---------|
| FR-A1 | 고객은 회원가입/로그인할 수 있다 (역할: 고객/상담사/관리자) | 전제 조건 | Must |
| FR-A2 | 고객은 본인 외 **가족 피검자**를 등록·관리할 수 있다 (이름, 생년, 관계) | P2 | Must |
| FR-A3 | 검사 결과·예약·상담 기록은 계정이 아닌 **피검자 단위**로 귀속된다 | P2 | Must |
| FR-A4 | 가족 피검자 본인의 동의 절차(알림/서명) 관리 | P2, 민감정보 | Won't |

### B. 검사 결과 조회

| ID | 요구사항 | 근거 | 우선순위 |
|----|---------|------|---------|
| FR-B1 | 고객은 피검자별 검사 결과 목록과 상세(지표 수치 + 해설)를 조회할 수 있다 | 상담의 대상이 되는 데이터 | Must |
| FR-B2 | 검사 결과는 서비스 유형(종합 대사 분석, 음식물 과민증, 영양중금속 등)별로 수십 개 지표를 가진다 | 문제 상황 서술 | Must |
| FR-B3 | 검사(LIMS) 시스템과의 실데이터 연동 | 실제 운영 시 필요 | Won't |

### C. 예약 (셀프서비스)

| ID | 요구사항 | 근거 | 우선순위 |
|----|---------|------|---------|
| FR-C1 | 상담사는 자신의 상담 가능 시간대(30분 슬롯)를 등록·수정할 수 있다 | P1, P4 | Must |
| FR-C2 | 고객은 **시간 기준으로 통합된** 가용 슬롯을 조회하고 즉시 예약할 수 있다 (담당자 개입 없음). 시스템이 해당 시간대 가용 상담사 중 예약 부하가 적은 사람을 자동 배정한다 | P1, P3 | Must |
| FR-C3 | 고객은 결과지의 **QR 코드**로 진입해 이름·전화번호 검증 후, 해당 결과지가 미리 선택된 예약 화면으로 바로 이동할 수 있다 | P1 | Must |
| FR-C4 | 예약 시 **피검자와 검사 결과를 선택**하고 사전 문의 내용을 남길 수 있다 (QR 진입 시 자동 선택) | P2, 상담 품질 | Must |
| FR-C5 | 동일 슬롯에 대한 동시 예약 시도 시 한 건만 성공한다 (이중 예약 원천 차단) | P4 | Must |
| FR-C6 | 고객/상담사는 예약을 취소할 수 있으며, 취소된 슬롯은 즉시 재예약 가능해진다 | P3, P4 | Must |
| FR-C7 | 고객은 만석 시간대에 **대기 신청**을 할 수 있고, 취소 발생 시 해당 날짜 대기자 전원에게 알림 → 선착순 재예약 | P3 | Should |
| FR-C8 | 만석 시간대 조회 시 **가장 가까운 빈 슬롯을 추천**한다 | P3 | Should |
| FR-C9 | 재상담 고객은 배정 시 이전 상담사의 슬롯을 우선 배정한다 (하이브리드 배정) | 상담 연속성 | Should |
| FR-C10 | 예약 변경(일정 변경) 기능 | 운영 편의 | Could |

|----|---------|------|---------|
| FR-D1 | 예약 확정/취소 시 고객에게 알림을 발송한다 | P5 | Must |

### E. 상담 수행 및 기록

| ID | 요구사항 | 근거 | 우선순위 |
|----|---------|------|---------|
| FR-E1 | 상담사는 당일 상담 일정과 각 예약의 컨텍스트(**고객 연락처**, 피검자, 검사 결과, 사전 문의)를 한 화면에서 본다 — 전화 상담이므로 예약자 이름·전화번호는 필수. 배정 상담사에게만 노출 | P6, 상담 수행 | Must |

| FR-E3 | 상담사가 자유 텍스트 메모를 입력하면 **LLM이 구조화 필드로 자동 추출**해 초안을 채운다 | P6 (기록 부담 최소화) | Should |
| FR-E4 | 예약 확정 시 검사 결과 + 사전 문의를 바탕으로 **상담사용 사전 브리핑**을 LLM이 자동 생성한다 | 상담 준비 시간 단축 | Should |
| FR-E5 | 구매 이벤트 수신 웹훅(`/webhooks/purchase`)으로 완료 상담과 자동 대사하여 구매 연결 여부를 갱신한다 | P7 | Should |
| FR-E6 | 자사몰 GTM/GA4 → BigQuery export 기반 구매 데이터 파이프라인을 웹훅 공급원으로 연동 | P7 실운영 | Won't |
| FR-E7 | 통화 녹음 → STT 전사 → LLM 구조화로 상담 기록을 자동 생성한다 (상담사는 검수만) | P6 고도화 | Won't |

## 2.2 비기능 요구사항 (NFR)

| ID | 요구사항 | 근거 |
|----|---------|------|
| NFR-1 | **동시성 안전**: 이중 예약은 애플리케이션 로직이 아닌 DB 제약 수준에서 차단한다 | P4. 레이스 컨디션은 코드만으로 못 막음 |
| NFR-2 | **접근 제어**: 건강정보는 민감정보이므로 고객은 자신의 피검자 데이터만, 상담사는 배정된 예약의 데이터만 접근한다 | 의료 도메인 특성 |
| NFR-3 | **LLM 비용 효율화**: 실시간성이 불필요한 LLM 작업(사전 브리핑)은 비동기 배치 방식으로 처리하고, 실패해도 핵심 플로우(예약/상담)는 영향받지 않는다 | 운영 비용, 안정성 |
| NFR-4 | **확장 가능한 알림 구조**: 알림 발송을 채널 어댑터로 추상화하여 알림톡/SMS 추가 시 도메인 로직 무변경 | 실운영 전환 대비 |
| NFR-5 | **감사 가능성**: 예약 상태 변경 이력이 추적 가능해야 한다 (상태 + 타임스탬프) | 노쇼 분쟁, 지표 신뢰성 |
| NFR-6 | **재현 가능한 실행 환경**: 평가자가 명령 1~2개로 전체 시스템(시드 데이터 포함)을 구동할 수 있어야 한다 | 과제 제출물 특성 |
| NFR-7 | **QR 토큰 보안**: QR에는 raw ID가 아닌 서명된 토큰을 담고, 토큰 소지 + 이름/전화번호 일치 검증을 통과해야 예약 플로우에 진입한다 | raw ID 노출 시 열거 공격(IDOR)으로 타인 건강정보 접근 가능 |
| NFR-8 | **시간 처리**: DB는 UTC(timestamptz)로 저장, 표시·해석은 Asia/Seoul 고정 | 국내 전화 상담 서비스로 멀티 타임존 요구 없음. 저장만 표준 준수해 확장 여지 확보 |
| NFR-9 | **LLM 전송 데이터 최소화**: 외부 LLM API에는 이름·연락처 등 식별자를 제거하고 지표 수치·해설·사전 문의만 전송한다 | 건강정보는 민감정보. 외부 전송 범위를 업무 목적 최소한으로 제한 |
| NFR-10 | **키 없는 재현성**: API 키가 없어도 전 기능이 동작해야 한다 — LLM 어댑터는 키 부재 시 결정론적 목 구현체로 자동 폴백하고, 키가 있으면 실 API(동기 + Batch)로 동작한다 | 평가자가 외부 계정 없이 `docker compose up`만으로 전체 플로우를 재현 (NFR-6의 강화). LLM이 보조 수단이라는 원칙(NFR-3)의 구현적 귀결 |

## 2.3 범위 제외(Won't) 항목의 공통 근거

- **커머스 파이프라인(GTM/GA4→BigQuery), LIMS 연동, 실제 전화(VoIP), 실채널 알림 발송**: 외부 시스템 의존이 커서 2주 과제에서 목(mock) 이상의 가치를 만들기 어렵다. 대신 **연동 지점을 인터페이스(구매 웹훅, 알림 채널 어댑터)로 설계에 명시**하여 확장 경로를 보여준다.
- **동의 절차, 고급 분석**: 핵심 문제(수동 운영 → 자동화) 해결과 직접 관련이 없어 후순위.
